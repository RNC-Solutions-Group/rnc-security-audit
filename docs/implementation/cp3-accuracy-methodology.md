# CP3 accuracy methodology

> The production detector never grades its own output. Truth manifests are
> authored outside the scanner input root and are read only by test tooling.

## Corpus tiers

| Tier | Source | Purpose | Accuracy claim |
| --- | --- | --- | --- |
| 1 | CP0-CP2 synthetic v0/v1/edge corpora | Contract, streaming, policy, reporting and cross-backend regression | Execution correctness only; not production credential accuracy |
| 2 | `tests/fixtures/providers/tier2` + `tests/cp3/provider-truth-tier2.json` | Controlled provider-format positives, negatives and edge cases | Exact byte-range provider-format accuracy on this authored corpus |
| 3 | `tests/fixtures/providers/tier3` + `tests/cp3/provider-truth-tier3-heldout.json` | Separately specified held-out corpus, not tuned per rule | Reported separately; same limitations as Tier 2 |
| 4 | `tools/cp3/challenge.py` + `tests/cp3/independent-challenge-truth.json` | Hand-authored challenge that does not reuse the Tier 2/3 generator, templates or seeds | Reported separately; first-party authored, not externally sourced |
| 5 | Levain FP/TP corpus, Leaky Repo, Gitleaks comparison | External, licensed, isolated evidence | Only the scoped metric stated for each corpus |

Tier 1 is preserved byte-for-byte where its contracts require it. It is never
counted as production credential accuracy.

## Shared generator dependency and independence

Tier 2 and Tier 3 are separately specified and scored, but both are generated by
`tools/cp3/fixtures.py` and therefore share:

- the placeholder renderer and deterministic seed convention;
- the token alphabet and fixture layout patterns;
- the first-party author's style and assumptions about provider formats.

They are controlled provider-format corpora, not independent evidence of broad
generalization. That shared dependency is now explicit rather than implied by
the labels "Tier 2" and "Tier 3".

The Tier 4 challenge is implemented in [`tools/cp3/challenge.py`](../../tools/cp3/challenge.py).
It does not import or reuse `tools/cp3/fixtures.py`, its templates, the same
seed strings, or the same fixture layout. It is still authored by the same
project, so it is **not** an externally sourced corpus and is not described as
one. It includes:

- ordinary AWS IAM resource identifiers that must not become findings;
- `ABIA`/`ACCA` sensitive identifiers with distinct rules;
- legacy and stateless GitHub App installation tokens;
- two occurrences of the same npm token in one file;
- UTF-8 multibyte content and CRLF;
- a public-key lookalike, documentation values and malformed tokens;
- a multiline modern installation token.

## Truth ownership

`tools/cp3/fixtures.py` constructs Tier 2/3 source bytes from declared templates
and records placeholder byte spans while rendering. It does not invoke the
detector. `tools/cp3/challenge.py` constructs Tier 4 in the same spirit but with
its own hand-authored fixtures. Truth manifests are written outside the scan
root. They contain:

- path, exact start/end byte, line start/end;
- expected rule and credential family;
- SHA-256 of the exact matched bytes;
- source-file SHA-256 and length;
- required scope.

`tools/cp3/score.py` re-verifies the truth against source bytes before scoring.
A missing file, changed hash, changed length, changed line mapping or duplicate
truth identity fails the scoring run. Detector output cannot alter truth.

The historical Tier 2/Tier 3 manifests and their scores are preserved as
historical evidence. The corrective work did **not** rewrite expected items to
match the detector. The AWS taxonomy suite is a new independently authored
manifest and does not change the old manifests.

## Byte-addressed classification

Each finding must match an expected item by:

1. source path;
2. exact `start_byte` and `end_byte`;
3. expected `rule_id` (strict true positive).

Classification:

| Classification | Meaning |
| --- | --- |
| `EXPECTED_DETECTION` | Exact byte span and rule match |
| `MISSED_EXPECTATION` | Expected item has no exact finding |
| `FALSE_POSITIVE` | Finding has no truth item at a known path/span |
| `MISALIGNED_MATCH` | Byte range overlaps but is not exact |
| `WRONG_RULE` | Span and family match, rule identity differs |
| `WRONG_FAMILY` | Span matches, credential family differs |
| `DUPLICATE` | Same expected occurrence claimed more than once |
| `AMBIGUOUS_MATCH` | Finding or truth overlaps multiple items |
| `UNMAPPED` | Finding path is outside the truth manifest |

`precision = TP / (TP + FP)`, `recall = TP / (TP + FN)`, and
`F1 = 2PR/(P+R)`. Undefined denominators produce `null`, never a fabricated
100%.

Wrong-family, wrong-rule and misaligned findings are false positives for strict
precision. Duplicate observations never add TP. Ambiguous observations never add
TP or FP. If a truth span is ambiguous with another truth, it is counted as
missed for conservative recall; it is **not** silently removed from the
denominator. The `unscored_truth` metric makes that choice visible.

Same-line occurrences are distinguished by byte range. A dedicated fixture and
negative control prove two occurrences on one physical line are two findings,
not a duplicate or an ambiguity.

## AWS classification methodology

`tests/cp3/aws-identifier-taxonomy.json` defines 20 cases derived from the AWS
IAM identifiers documentation. The Rust suite constructs synthetic values at
test time and checks every case under both modes and all four strategies.

Expected behavior:

- `AKIA` and `ASIA` map only to `aws-access-key-id`;
- `ABIA` maps only to `aws-sts-service-bearer-token-id`;
- `ACCA` maps only to `aws-context-specific-credential-id`;
- `AIDA`, `AGPA`, `AIPA`, `ANPA`, `ANVA`, `APKA`, `AROA` and `ASCA` produce no
  credential finding;
- malformed prefix/length/charset and the AWS documentation placeholder produce
  no finding;
- multiple identifiers on one line remain distinct occurrences;
- resource identifiers embedded in a realistic IAM JSON policy do not produce
  findings, while a genuine `AKIA` in that policy does.

The AWS documentation does not make `ABIA` an ordinary access key: it identifies
the access-key-ID component of a service bearer token. `ACCA` is documented only
as a context-specific credential prefix. Their dedicated rules return
`PLAUSIBLE_UNVERIFIED` with identifier-only notes.

## GitHub installation-token methodology

The suite is [`crates/rnc-core/tests/github_installation.rs`](../../crates/rnc-core/tests/github_installation.rs).

- Legacy `ghs_` opaque tokens are 40 characters total and validated as
  alphanumeric bodies.
- Stateless `ghs_APPID_JWT` tokens are treated as opaque client credentials. The
  validator checks only documented framing: `ghs_`, a bounded app ID, `_`, and
  three bounded base64url segments separated by exactly two dots.
- Variable segment lengths are accepted within bounds. No single hardcoded
  length, signature, issuer or claim is trusted.
- Malformed, placeholder, incomplete and oversized values are not emitted.
- Punctuation, multiple tokens on one line, stream boundary crossings, all
  strategies and resource exhaustion are tested.

Modern findings are `PLAUSIBLE_UNVERIFIED` and have their confidence downgraded.
That is deliberate: the token is recognizable but its validity cannot be
established offline.

## Execution gate

Accuracy is not scored when:

- execution is `ERROR`/`INTERRUPTED`, result is `FAILED` or `INCOMPLETE`;
- evidence is invalid;
- a required unit is uninspected;
- a truth file was not inspected;
- the result code is not a completed detection result.

A missed required file is an execution-coverage failure, not merely a false
negative. The two facts are reported separately and never double-counted.

## Independent external harness

The pinned harness revision is
`86de44bf1cb13abf9a0c375a8b91d102c9b6dc9f`. It is line-addressed. The adapter
preserves byte offsets in metadata and exports an independently generated
line-range truth manifest. On Tier 2 the line-only harness matches **25** of 27
expected items and reports **2 ambiguous** same-line occurrences because two
distinct token spans share a line. The byte scorer classifies both correctly.
The line-only result is compatibility evidence, not the authoritative accuracy
score. No external repository is modified.

## External corpora

### Levain

The MIT-licensed Levain corpus supplies 116 negative sections and 45 positive
sections. Only credential kinds matched by a declared RNC family are included in
the denominator; unsupported kinds are reported separately. A finding that
overlaps a corpus secret of an unsupported kind is marked out of scope rather
than false positive. The negative corpus is a precision stress test: every
reported finding is counted as a false positive.

Current scoped result on the pinned revision: **30/31 mapped positives** with
**0** negative-corpus findings, **0** false positives on mapped families and
**5** out-of-scope observations. The single mapped miss is a deliberately
malformed PEM whose base64 body is not decodable; RNC rejects it by design. This
is recorded as a false negative, not converted into success.

The Levain oracle does not label AWS resource identifiers as credentials; the
AWS catalog now produces no findings for those identifiers. The external run was
re-executed after the catalog change and its scoped score did not change.

### Leaky Repo

Leaky Repo supplies count-based file inventory, not credential-level truth. RNC
reports actual findings and `min(observed, expected)` count coverage only. No
TP/FP/precision/recall is claimed. Excess findings are not automatically false
positives. Current pinned result is unchanged: 33 observed, 33/175 count
coverage, 18/44 files, zero excess and zero unlisted findings.

### Gitleaks comparison

A pinned local Gitleaks build (`sha256:c8bf14bc271caf34692dc76ea008f7932b4916fcf27254440e178775177ffc98`)
is run with its native default configuration on the same filesystem fixtures.
Rule IDs are mapped to broad families, not assumed equivalent.

One-to-one reconciliation:

- one observation may claim at most one truth occurrence;
- one truth occurrence may be claimed by at most one observation;
- source path and exact byte occurrence must match;
- Gitleaks line/column values are reconstructed using its actual report contract
  (columns are relative to the previous LF byte, not the first content byte);
- repeated values require a verified position; otherwise the observation is
  ambiguous, not a guessed TP;
- wrong position, wrong file, wrong family and unknown rule IDs are not TPs;
- duplicates do not add TP;
- matching is deterministic and independent of report ordering.

Corrected controlled-corpus result:

| Dataset | TP | FP | FN | Duplicates | Ambiguous | Unscored | Precision | Recall | F1 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Tier 2 | 22/27 | 0 | 5 | 2 | 0 | 0 | 100% | 81.48% | 89.80% |
| Tier 3 | 11/15 | 0 | 4 | 0 | 0 | 0 | 100% | 73.33% | 84.61% |

The original pre-correction Tier 2 result was 22 TP / 2 FP / 5 FN (precision
91.67%, F1 86.28%). The two former false positives were duplicate decoded
private-key observations at the same source span; the corrected reconciler
classifies them as duplicates, not additional TP or FP. Tier 3 was unchanged.
The original measurements are preserved in this report's historical section and
in the prior CI artifact.

Eighteen comparator negative controls cover zero findings, report-everything,
repeated secrets, one observation versus two expectations, two observations
versus one expectation, two secrets on one line, wrong position, wrong file,
wrong family, overlap, multiline, assignment context, malformed metadata,
duplicate identities, unknown rules and order independence.

RNC itself remains **27/27**, **15/15** and **14/14** on the three controlled
corpora. These are independent truth standards; the RNC and Gitleaks numbers are
not a general product ranking.

## Reproduction

```sh
cargo build --release --workspace --locked
python -m tools.cp3.integration_check \
  --binary target/release/rnc --output artifacts/cp3/integration.json
python -m tools.cp3.score \
  --findings /private/tier2.json \
  --truth tests/cp3/provider-truth-tier2.json \
  --rules rules/rnc-providers-v1.json \
  --source-root tests/fixtures/providers/tier2 --require-perfect
python -m tools.cp3.external_check \
  --harness-root /pinned/scanner-harness \
  --findings /private/tier2.json \
  --truth tests/cp3/provider-truth-tier2.json \
  --rules rules/rnc-providers-v1.json
python -m tools.cp3.external_corpora --help
python -m tools.cp3.comparative --help
```

The Tier 4 challenge is built by `tools/cp3/challenge.py` and scored by the same
byte-addressed scorer. Its manifest is checked for reproducibility; it is not a
replacement for the historical Tier 2/3 truth.
